# Hailcast: forecasting evaluation

> Generated by `python backend/scripts/generate_reports.py` on 2026-11-15 21:19 UTC. Do not edit by hand; rerun the script.
>
> **The data is synthetic.** `backend/app/data/download_sample.py` generates trips shaped like NYC TLC yellow-taxi records with a fixed random seed. They are replayed as if they were live; they are not real trips and not live traffic.

## 1. What is forecast

City-wide taxi pickups per hour (all zones summed), one hour ahead. Zone-level numbers in the
dashboard split that city-wide forecast by each zone's historical share for the hour of day.

## 2. Data used in this run

- 10,672 sample trips loaded through the batch pipeline: 10,672 stored in Bronze,
  10,672 passed validation into Silver, 1,812 zone-hour rows in Gold.
- 167 complete city-wide hours from 2026-11-01 00:00 to
  2026-11-07 22:00. The newest hour is dropped because it may still be filling.
- The first 24 hours are dropped because they have no full 24 hours of history
  for the lag features, leaving 143 hours to train and test on.

## 3. How leakage is prevented

1. **Walk-forward splits.** `TimeSeriesSplit(n_splits=3)`: each fold trains on an expanding window and
   tests on the hours that follow it. Rows are never shuffled.
   Check on this run, every training window ends before its test window starts: **yes**.
2. **Past-only features.** Every lag and rolling mean is shifted by at least one hour, so the value
   being predicted is never an input. Hours without a full history are dropped, not back-filled.
   `backend/tests/test_reliability.py::test_features_never_use_the_future` changes demand from each
   hour onwards, the first hour included, and asserts that no feature of that hour or earlier moves.
3. **Baselines get the same folds.** The hour-of-day average is fitted on the training window only.

## 4. Result under the pre-registered rule

The question, the baselines and the decision rule were fixed before this run, in
[forecast_evaluation_preregistration.md](forecast_evaluation_preregistration.md).

**LightGBM is not shown to beat the strongest baseline, "same hour yesterday".** LightGBM misses by 13.89 trips per hour, the baseline by 13.26, and the 95% interval for the difference includes zero.

- Comparator: the baseline with the lowest MAE over all 105 test hours, **same hour yesterday**.
- Mean of (LightGBM error − baseline error) per hour: **+0.64** trips, 95% interval
  **-5.46 to +2.78** (moving block bootstrap: 24-hour blocks, 2,000 resamples, seed 0).
  Below zero means LightGBM is closer to the actual demand.
- LightGBM has the lower MAE in 0 of 3 folds. This is reported, not used to decide.

## 7. Limits

- The data is synthetic and covers about 7.0 days, so each test window is only
  35 hours. The numbers show the method works end to end; they are not evidence
  about real New York demand.
- No weekly seasonality can be learned from less than two weeks of data.
- Accuracy is measured one hour ahead. The dashboard's multi-hour forecast feeds its own predictions
  back in, so error grows with the horizon; the shaded band there uses 1.28 x RMSE as a rough 80% range.
- MAPE is unstable in quiet night hours where actual demand is close to zero.
- The generator is a fixed daily curve plus noise, which suits "same hour yesterday" by construction.

## 8. Reproduce

```bash
python backend/scripts/generate_reports.py   # rewrites this file and docs/eda_report.md
python -m pytest                             # leakage, pipeline and reliability tests
```

In the running app, `POST /api/v1/ml/train` runs the same evaluation on whatever is in the Gold table
and appends the result to `backend/app/ml/saved_models/experiments_registry.json`.
