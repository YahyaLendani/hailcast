# Security review

Scope: the hosted demo at hailcast.onrender.com and the code in `backend/`. Reviewed
2026-11-16. The demo serves synthetic trip data only. It holds no personal data, has
no user accounts and sets no cookies.

## What a visitor can reach

| Endpoint | Access | Why |
| --- | --- | --- |
| `GET` analytics, health, ML results, `/api/info`, the dashboard | Public | Read-only views of synthetic data. |
| `POST /api/v1/ml/forecast` | Public | One prediction from a saved model; `horizon_hours` is capped at 168. |
| `POST /api/v1/stream/control` | Public | Replays the built-in sample only. Speed (≤100×) and batch size (≤500) are capped by the schema. |
| `WS /ws/stream`, `GET /api/v1/stream/sse` | Public | Pushes the replay to the dashboard. |
| `POST /api/v1/ml/train` | Public, **cooldown** | The dashboard's retrain button calls it. Training is the heaviest work the server does. |
| `POST /api/v1/health/jobs/{name}/run` | Public, **cooldown** | The dashboard's run-now buttons call it. Unknown job names return 404. |
| `POST /api/v1/ingest/*` | **API key** when `API_KEY` is set | These write arbitrary data into the pipeline. |

## Controls

**API key for uploads** (`app/core/security.py`). When `API_KEY` is set, which Render
does on the hosted demo with a generated value, the `/ingest` routes need it in the
`X-API-Key` header. The comparison uses `secrets.compare_digest`, so its timing does not
reveal how much of a guess was right. Tested in `test_reliability.py`.

**Cooldown for expensive actions.** Retraining and each pipeline job can run at most once
per `EXPENSIVE_ACTION_COOLDOWN_SECONDS` (default 300). A repeat inside the window gets
`429 Too Many Requests` with a `Retry-After` header, and the dashboard shows the message.
A valid API key skips the wait, so the operator is never blocked. Tested in
`test_security.py`.

The window is shared by every caller, not kept per client. The goal is to cap the
server's work, and client addresses behind Render's proxy are easy to vary. The cost is
that one visitor's retrain makes the next visitor wait. On a demo that is acceptable.

**CORS.** Browsers only let other sites call the API from the origins in `CORS_ORIGINS`.
The served dashboard is same-origin and needs none; the default allows the local Next.js
prototype at `http://localhost:3000`. Credentials are off because the API uses no
cookies, and only `GET`/`POST` with `Content-Type` and `X-API-Key` are allowed. Before
this review the policy was every origin with credentials on. Tested in
`test_security.py`.

**Input limits.** Pydantic schemas bound trip fields, forecast horizon, replay speed and
batch size, and `seed-sample` takes at most 10,000 trips. Where the dashboard builds HTML
from API data, text goes through its `esc()` helper and the rest is numbers and dates
formatted by the browser's `Intl` formatters, so API values cannot inject markup.

**Secrets.** No secret is committed. `API_KEY` is generated by Render
(`render.yaml`, `generateValue: true`) and read from the environment.

## Risks accepted

- **Anyone can pause or stop the shared replay.** All visitors watch one stream. Locking
  it would break the demo's main interaction, and the worst case is a stopped replay
  that the next visitor restarts.
- **Batch uploads have no size cap.** They need the API key, so only the operator can
  send one.
- **The cooldown lives in memory.** It resets when the server restarts, and two server
  processes would each keep their own. The demo runs one process
  (`WEB_CONCURRENCY=1`).
- **No general rate limit on reads.** Read endpoints are cheap queries on a small
  SQLite database. Render's free tier is the outer limit.

## Out of scope

User accounts, login and sessions: the demo has no user data to protect. Network-level
protection (TLS, DDoS) is Render's.
